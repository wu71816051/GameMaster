### 架构设计

基于 [角色卡系统分层架构设计](./character-card-architecture.md)，CoC7 规则系统采用以下分层架构：

```
战斗/游戏层
    ↓
规则服务实现层 (rule/coc7/)
  • CoC7CharacterService ✨ 设计中
    ↓
规则适配器层 (rule/coc7/)
  • CoC7Adapter ✅ 已实现
    ↓
全局角色卡服务层 (core/services/)
  • CharacterService ✅ 已实现
    ↓
规则服务接口层 (core/interfaces/)
  • IRuleCharacterService ✨ 设计中
```

### 核心原则

- **全局服务** (core) - 提供数据持久化和通用接口
- **规则服务接口** (core) - 定义规则角色卡服务的标准接口 ✨ 新增
- **规则服务实现** (rule) - 各规则系统实现具体接口 ✨ 新增

  - 支持者: 不用检定或难度-1
  - 缺乏强烈感受: 无调整
  - 强烈反对: 难度+1~2
  - 玩家支持论点: 难度-1
- ❌ **多人说服**: 协作社交检定

## 💾 数据库改动状态

### 当前状态：✅ **不需要数据库改动**

**原因**：
1. 现有数据库结构已支持多规则系统
   - `character.attributes` 和 `character.skills` 使用 JSON 灵活存储
   - `character.metadata` 可存储规则系统特定数据（疯狂状态、战斗状态等）
   - `conversation.metadata` 可存储会话级别配置（骰子修正等）

2. 已实现功能充分使用数据库
   - `.san` 命令：✅ 持久化 SAN 值到 `character.attributes`
   - `.精神治疗` 命令：✅ 更新 SAN 值和疯狂状态到 `character.metadata`
   - `.奖励骰/.惩罚骰` 命令：✅ 存储骰子修正到 `conversation.metadata`

3. 所有功能都能基于现有结构正常工作
   - 角色数据读取：通过 JSON 字段
   - 命令验证：通过中间表查询会话
   - 帮助系统：动态生成，无需存储

### 未来可能需要的数据库改动

如需持久化游戏状态，可以考虑：

#### 选项 1：使用现有 metadata 字段（推荐）
- 使用 `conversation.metadata` 存储临时状态（奖励骰等）
- 使用 `character.metadata` 存储成长标记
- **优点**：无需改动数据库结构
- **缺点**：查询效率较低

#### 选项 2：新建专用表（适合大规模数据）
```typescript
// 理智历史记录表
interface SanityHistory {
  id: number
  character_id: number
  conversation_id: number
  old_value: number
  new_value: number
  reason: string  // "遭遇恐怖", "魔法施放" 等
  timestamp: Date
}

// 技能成长历史表
interface SkillAdvancement {
  id: number
  character_id: number
  skill_name: string
  old_value: number
  new_value: number
  timestamp: Date
}

// 战斗日志表
interface CombatLog {
  id: number
  conversation_id: number
  round: number
  actor_type: string  // "pc", "npc"
  actor_id: number
  action: string  // "attack", "dodge", "skill_check"
  target_id?: number
  result: string  // JSON: 详细结果
  timestamp: Date
}
```

**建议**：先完善核心功能，使用内存存储临时状态，稳定后再考虑持久化。
